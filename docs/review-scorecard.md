### Розбіжності з ключем — хто правий

Згідно з порадою walkthrough, кожну знахідку поза ключем перевірено, перш ніж зарахувати її
хибною тривогою.

| PR · знахідка | Рішення | Чому |
|---|---|---|
| PR-1 F4 (R11: тест не перевіряє `items`) | **нейтрально** | Слушно: тест зелений попри 1-D1. Ключ згадує це всередині 1-D1, окремим дефектом не рахує. |
| PR-2 F4 (R13: опис не згадує `feeText`) | **FP** | Пропуск поля в описі — не хибне твердження (§10 — про твердження, яких код не виконує). |
| PR-3 F4 (R10: експорт без сторінок) | **FP** | FP відносно ключа: CSV-експорт за своєю природою віддає весь файл. Рев'юер застосував R10 буквально — R10 прямо називає учасників і не виключає експортів. Причина в формулюванні правила, не в судженні → пункт для Task C. |
| PR-3 F5 (R12: тест відмови лише для `null`) | **нейтрально** | Слушно, і саме тому 3-D1 пройшов тести. Ключ згадує це всередині 3-D1. |
| PR-5 F1 — серйозність critical, у ключі medium | рахується як TP | Правила ключа: серйозність може не збігатися. Рев'юер аргументував «wrong money» (рубрика серйозності в `review-pr.md`). |
| PR-6 F3 — порожній рядок, а не рядок без email | рахується як TP (6-D3) | Той самий клас: відсутня валідація рядка → `undefined` у записі. |

**Пропуски.** В обох пропущених дефектах рев'юер **процитував** потрібний рядок, але не назвав дефекту:

- **2-D1:** процитовано рядок `email: db.findMember(...)`, але не зіставлено з видаленою мапою
  `names` (і другим викликом `findMember` для `member`). Продуктивності (O(n·m)) немає в жодному
  правилі R1–R20.
- **6-D2:** процитовано рядок з `db.members.length + 1`. Унікальність id формально покриває R20
  («мутація спільних масивів `db`» є і в стандарті, і в чек-лісті команди), але рев'юер її не
  перевірив.

Тобто один клас потрібно додати в стандарт, а другий там уже є — рев'юер його не застосував.
Матеріал для Task C.
